# 구현 계획 (plan.md)

`plan.md`는 **코드를 쓰기 전에 구현 방식을 리뷰할 수 있게 만드는 문서**다.

전통적인 개발에서는 구현 방법이 개발자의 머릿속에 있었고, 리뷰어가 처음 보는 건 완성된 diff였다. 그때는 이미 되돌리는 비용이 비싸다. plan.md는 **아직 문서를 고치는 것만으로 방향을 바꿀 수 있을 때** 설계를 검토하게 만든다.

## 도구가 만드는 계획 파일과 plan.md는 다른 것이다

이 구분을 놓치면 스킬 전체가 무의미해진다.

| | 도구가 자동 저장하는 계획 파일 | plan.md |
|---|---|---|
| 위치 | 도구의 개인 설정 폴더 | 레포의 `docs/plans/` |
| 성격 | 세션 작업 데이터 | 커밋되는 산출물 |
| 수명 | 보존 기간 후 자동 삭제 | git이 영구 보존 |
| 공유 | 개인 머신에만 존재 | 팀 전체가 읽음 |
| 승인 기록 | 없음 | 커밋/PR이 곧 기록 |

에이전트의 계획 모드는 계획을 **만드는 도구**고, plan.md는 그중 승인된 버전을 **레포로 승격시킨 것**이다. 자동 저장은 초안까지 전부 포함하지만, 남아야 하는 건 심문을 거쳐 확정된 하나다.

도구에 따라 그 저장 경로를 프로젝트 안으로 돌릴 수도 있다. 다만 그렇게 해도 **승인 시점에 커밋하는 행위는 별도로 필요하다.**

## 절차

### 1. 파일을 수정할 수 없는 상태에서 시작한다

계획을 세우는 동안 에이전트는 코드베이스를 읽을 수 있어야 하지만 파일을 쓰지는 못해야 한다. 이건 권고가 아니라 **권한으로 강제하는 것**이다 — 그래야 계획 중에 실수로 코드가 바뀌는 일이 구조적으로 불가능해진다.

쓰는 도구에서 이 상태에 해당하는 모드를 확인하고 그것으로 시작하라. 도구별로 이름이 다르므로, 어느 모드가 여기에 해당하는지는 각 도구의 지침 파일에 적어둔다.

세션에 넣을 것:

- `docs/intent/NNN-*.md` — 왜 만드는지
- `docs/specs/NNN-*.md` — 무엇을 만족해야 하는지
- `AGENTS.md` — 이 프로젝트에서 일하는 방식

spec이 없는 작은 작업이라면 intent만으로도 된다. 둘 다 없다면 먼저 만들어야 하는지 사용자에게 확인하라.

### 2. 계획을 뽑는다

네 가지가 반드시 들어간다.

- **Files** — 바뀌는 파일 목록. 신규/수정을 구분한다.
- **Order of work** — 작업 순서. 각 단계가 끝났을 때 어떤 상태인지 알 수 있게.
- **Risks** — 이 변경으로 깨질 수 있는 것, 마주칠 제약.
- **Proof** — 성공을 어떻게 증명할지. spec의 Acceptance criteria와 연결한다.

### 3. 계획을 심문한다 — 이 단계를 건너뛰지 마라

계획을 받아들이기 전에 반드시 되묻는다. 이게 plan.md의 값어치가 나오는 지점이다.

- 이 변경으로 **깨질 가능성이 있는 곳**은 어디인가?
- 가장 **위험한 단계**는 몇 번인가? 왜?
- **선택하지 않은 다른 방법**은 무엇이었고, 왜 이걸 골랐나?
- spec의 요구사항 중 **이 계획이 다루지 않는 것**이 있나?
- 되돌려야 할 때 어떻게 되돌리나?

답이 얄팍하면 계획이 얄팍한 것이다. 다시 뽑아라.

### 4. 합격 기준: 낯선 사람 테스트

**이 대화를 한 번도 보지 않은 엔지니어가 plan.md만 읽고 구현할 수 있는가?**

이게 왜 중요하냐면, 실제로 구현하는 건 그 대화를 못 본 다른 세션이나 서브에이전트이기 때문이다. 에이전트는 세션 간 기억을 공유하지 않는다. plan.md는 제로에서 시작하는 상대에게 맥락을 통째로 넘기는 장치다.

계획을 다 쓴 뒤 스스로 점검하라. "이 문장은 아까 대화에서 나온 배경을 알아야 이해되는가?" 그렇다면 그 배경을 문서에 적어라.

### 5. 커밋한다

```
docs/plans/
├── 001-claims-status.md
└── 002-social-login.md
```

intent·spec과 **같은 번호·슬러그**를 쓴다. 커밋 메시지는 `plan: 간편 로그인 개선`.

### 6. 구현하고, 벗어나면 갱신한다

계획이 승인되면 구현한다. 계획이 충실하면 대개 한 번에 끝난다.

**구현이 계획에서 벗어나면 같은 커밋에서 plan.md를 갱신한다.** 이게 규율이다. 코드와 계획이 어긋난 채로 머지되면 plan.md는 그 순간부터 거짓말이 되고, 리뷰가 diff를 계획과 대조하는 것도 무의미해진다.

동기화를 확실히 하고 싶다면 git 훅이나 CI 검사로 강제할 수 있다 — 구현 파일이 바뀌는 커밋에 plan.md 변경이 없으면 경고하거나 차단하는 식이다.

## 템플릿

```markdown
# Plan: 간편 로그인 개선
출처: docs/intent/002-social-login.md, docs/specs/002-social-login.md · 상태: draft

## Files
- auth-api/src/oauth/provider.ts (신규) — provider 추상화
- auth-api/src/oauth/google.ts (신규)
- auth-api/src/oauth/apple.ts (신규)
- auth-api/src/routes/login.ts (수정) — 콜백 라우트 추가
- auth-api/migrations/0042_add_provider.sql (신규)
- mobile-app/src/screens/Login.tsx (수정)
- auth-api/tests/oauth.test.ts (신규)

## Order of work
1. provider 추상화 인터페이스 추가. 이 시점에 기존 동작은 그대로다.
2. 마이그레이션으로 users에 provider, provider_uid 컬럼 추가 (nullable).
3. Google provider 구현 + 단위 테스트.
4. 이메일 충돌 처리 (spec R3) 구현. 여기가 회귀 위험이 가장 큼.
5. Apple provider 구현. private relay 케이스 포함.
6. 로그인 화면 버튼 연결.

## Risks
- 4번이 기존 이메일 로그인 경로를 건드린다. 기존 로그인
  통합 테스트가 통과하는지 각 단계마다 확인.
- provider 토큰이 에러 로그에 실릴 수 있다 (spec N2, 정책 위반).
  에러 핸들러에서 명시적으로 마스킹 필요.
- 마이그레이션은 nullable로 추가해 롤백 가능하게 유지.

## Proof
- oauth.test.ts가 spec AC1~AC3을 커버한다.
- 기존 auth 통합 테스트 전부 통과.
- 로그인 화면 스크린샷이 승인된 목업과 일치.
- 에러 로그에 provider 토큰이 없음을 테스트로 확인.

## Alternatives considered
- provider별 라우트를 따로 두는 방식: 중복이 커지고 세 번째
  provider 추가 시 비용이 늘어 추상화 계층을 택함.
```

## 검증 루프를 함께 설계한다

Proof 섹션이 실제로 돌아가려면 에이전트가 **사람에게 넘기기 전에 스스로 검증**할 수 있어야 한다. 계획을 세울 때 다음을 확인하라.

- 테스트·빌드·린트가 **각각 한 명령으로** 실행되는가? (`make test`, `npm test` 등) 아니라면 그것부터 계획에 넣어라.
- 성공 상태가 **정량적으로** 정의돼 있는가? "잘 동작한다"가 아니라 "oauth.test.ts 전부 통과".
- UI 작업이라면 스크린샷을 찍어 목업과 대조할 수단이 있는가?

### 버그 수정이라면 순서가 다르다

1. 먼저 **실패하는 테스트**를 쓴다.
2. 그 테스트가 **예상한 이유로** 실패하는지 확인한다.
3. 그 상태로 커밋한다.
4. 그다음 코드를 고쳐 통과시킨다. **테스트는 수정하지 않는다.**

수정 이전부터 존재했고 고쳐 쓸 수 없었던 테스트가 버그가 사라졌다는 증거다. 에이전트가 손쉬운 길로 테스트를 고쳐버리지 못하게 도구의 편집 차단 설정으로 테스트 파일 편집을 막는 것도 방법이다.

## 규모별 차이

### 개인 / 소규모

- 심문 단계는 그래도 하라. 혼자여도 "뭐가 깨질 수 있지?"를 명시적으로 묻는 것과 안 묻는 것은 결과가 다르다.
- 작은 변경(파일 1~2개, 테스트가 이미 덮고 있는 영역)은 plan.md를 커밋하지 않고 계획 단계 안에서 끝내도 된다. 대신 **3개 파일 이상 건드리거나 한 문장으로 설명이 안 되는 변경**은 커밋하라.
- Alternatives considered는 나중에 자신에게 가장 유용한 섹션이다. 두 달 뒤 "왜 이렇게 했지?"를 답해준다.
- 가드레일(AGENTS.md, 훅, 권한 설정)이 자리잡기 전에는 자동 승인 모드를 켜지 마라. 계획이 좋아도 blast radius가 넓으면 사고가 난다.

### 팀

- plan.md는 **PR로 올린다.** 코드 PR과 분리하면 계획만 먼저 리뷰받을 수 있다. 리스크가 높은 변경일수록 이 분리가 값어치를 한다.
- 일상적인 변경은 담당 엔지니어가 승인하고, 조직이 고위험으로 분류한 변경은 테크리드나 아키텍트가 본다.
- 나중에 PR 리뷰에서 **diff가 plan.md와 일치하는지**를 검사 항목으로 넣어라. 원격 호스트의 PR 템플릿(`.github/pull_request_template.md`, GitLab이면 `.gitlab/` 아래)에 "변경이 spec.md, plan.md와 일치하는가"를 체크 항목으로 두면 된다.
- 병렬 작업으로 넘어갈 때 이 문서가 더 중요해진다. 세션마다 별도 worktree를 쓰면 서로의 컨텍스트를 전혀 모르므로, 공유되는 건 `AGENTS.md`와 작업별 spec·plan뿐이다. 병렬 세션은 두세 개부터 시작하라 — 한계는 모델이 아니라 **사람이 제대로 리뷰할 수 있는 흐름의 수**다.
- Order of work를 파일이 겹치지 않는 단위로 쪼개면 그대로 병렬 분배 계획이 된다. 겹치는 작업은 한 세션에서 순차로 처리한다.

## 흔한 실패

- **spec을 요약해놓고 계획이라 부르기.** 파일 경로와 순서가 없으면 계획이 아니다.
- **Risks를 형식적으로 채우기.** "예상치 못한 버그가 있을 수 있음" 같은 문장은 아무 정보가 없다. 구체적인 파일이나 동작을 지목하라.
- **Proof를 "테스트 작성"으로 적기.** 무엇을 증명하는 테스트인지, spec의 어느 기준에 대응하는지 적어라.
- **계획을 커밋하고 잊기.** 구현이 벗어났는데 갱신하지 않으면 문서가 거짓이 된다. 차라리 삭제하는 게 낫다.
- **심문 없이 첫 계획을 그대로 승인하기.** 계획 단계의 첫 출력은 초안이지 결론이 아니다.

## 다음 단계

구현이 끝나면 검증 루프를 돌리고 PR을 올린다. 리뷰 단계에서 이렇게 안내하라:

> 구현이 끝났습니다. plan.md의 Proof 항목을 모두 확인했고, 계획에서 벗어난 부분은 plan.md에 반영했습니다. PR 리뷰에서 diff와 plan.md를 대조하실 수 있습니다.
