# 요구사항과 설계 정리

기존 원본을 읽어 검증 가능한 요구사항과 설계 결정을 기록한다. 저장·승인 절차는 프로젝트 루트 `AGENTS.md`를 따른다.

## 진행

1. 원본 목록·현재 작업 상태·전체 공통 제약을 읽고 관련 의도 항목의 현재 승인본과 최신 제안을 구분한다. 의도 항목이 검색되지 않으면 원문과 이전 대응표도 확인한다.
2. 관련 코드 인터페이스·API 규격·Schema·정책과 기존 패턴을 읽는다. 이미 적합한 원본을 새 JSON에 중복 복제하지 않고 위치와 판단 근거를 연결한다.
3. 요구사항과 수용 기준은 확인 가능한 문장으로 적는다. 결정에는 이유·검토한 대안·예외를 보존한다. 구현 순서는 `plan` 항목과 구분한다.
4. 정책끼리 또는 요구와 예외가 충돌하면 각각의 근거, 포기하는 조건, 판단 주체를 미결 항목에 남기고 먼저 질문한다. 기한이 임박해도 미승인 예외를 승인된 요구에 섞지 않는다.
5. 새로운 항목은 `proposed`로 시작하며 실제 사용자 지시·승인 범위가 명확한 내용만 `accepted`로 기록한다. 기존 항목 변경은 다음 revision에 저장하고 이전 내용을 보존한다.
6. 변경된 항목의 역참조로 영향을 확인한다. 미결 사항은 답하거나 이월 이유를 적고 관련 ID로 다음 단계에 연결한다.
7. 원본·출처·관계·색인·작업 상태를 일괄 저장하고 재조회·검증한다. 구조 검증 통과와 설계 의미·승인 판단을 별도로 보고한다. 요청 없는 커밋·PR·상세 문서 생성은 하지 않는다.

화면 설계가 필요한 요청이면 관련 목업이 기존에 있는지 확인하고 설계 항목에서 참조한다. 정책 스킬이나 자동화는 실제 반복 필요가 확인되기 전 미리 만들지 않는다.

## 사람이 읽는 문서를 요청받은 경우

JSON 원본을 먼저 반영하고 파생 문서 표시, 관련 ID·revision 또는 Git commit을 붙인다. `docs/templates/spec.md`의 섹션을 사용한다. 아래는 실제 결정이 아닌 가상 예시다. 수치·승인·작성자·상태를 실제 근거 없이 복사하지 않는다.

```markdown
# Spec: 간편 로그인 개선
출처: docs/intent/002-social-login.md · 상태: draft

## Summary
Google·Apple OAuth 로그인을 추가해 신규 가입 경로를 단순화한다.
기존 이메일 로그인은 그대로 유지하며, 소셜 계정과 기존 계정의
중복 가입은 이메일 기준으로 차단한다.

## Requirements
### 기능 요구사항
- R1. 로그인 화면에 Google·Apple 버튼을 노출한다.
- R2. 최초 소셜 로그인 시 계정을 생성하고 즉시 세션을 발급한다.
- R3. 소셜 계정의 이메일이 기존 계정과 일치하면 가입을 차단하고
      기존 방식으로 로그인하도록 안내한다.

### 비기능 요구사항
- N1. OAuth 콜백 처리는 p95 800ms 이내.
- N2. 로그인 실패 사유를 사용자에게 노출하되 계정 존재 여부는
      추론할 수 없어야 한다.

## Design
### 흐름
1. 클라이언트가 provider 인증 페이지로 리다이렉트
2. 콜백을 auth-api가 수신, provider 토큰 검증
3. user-database에서 이메일 조회 → 신규/충돌 분기
4. 기존 세션 발급 로직 재사용

### 변경 지점
- auth-api: OAuth provider 추상화 계층 신규
- user-database: users 테이블에 provider, provider_uid 컬럼 추가
- mobile-app: 로그인 화면 버튼 추가

### 적용한 정책
- 보안 표준: provider 토큰은 로그에 남기지 않는다 (PII 분류)
- API 규약: 신규 엔드포인트에 게이트웨이 JWT 적용
- 접근성: 소셜 버튼에 명시적 label 제공

## Acceptance criteria
- AC1. 신규 Google 계정으로 가입 시 세션이 발급되고 홈으로 이동한다.
- AC2. 기존 이메일과 같은 Google 계정으로 시도하면 R3 안내가 뜬다.
- AC3. 인증 실패 시 provider 토큰이 어떤 로그에도 남지 않는다.

## Concerns
- C1. intent의 "새 PII를 수집하지 않는다"와 provider_uid 저장이
      충돌할 수 있다. provider_uid를 PII로 분류할지 판단 필요.
      → 판단 주체: 보안 담당
- C2. Apple의 이메일 가리기(private relay) 사용 시 R3의 이메일
      대조가 동작하지 않는다. 이 경우 정책 필요.
      → 판단 주체: Product Owner

## Open questions carried from intent
- 기존 이메일 계정과 소셜 계정 연결: 이번 범위에서 제외하되
  provider 컬럼 설계는 나중에 연결 가능하도록 남긴다.
```
