# Spec 작성 (spec.md)

`spec.md`는 **엔지니어가 계획을 세울 수 있는 수준의 요구사항·설계 문서**다. 전통적으로 분석가가 요구사항을 쓰고 디자이너가 그걸 다시 설계로 옮기던 두 단계를 한 세션으로 합친 것이다.

이 단계의 진짜 목적은 문서를 만드는 게 아니라 **정책을 작성 시점에 적용하는 것**이다. 보안 리뷰에서 몇 주 뒤에 발견되는 대신, 스펙이 써지는 순간 정책이 읽히고 반영된다.

## 시작 전 확인

1. `docs/intent/` 에서 대상 intent.md를 읽는다. 없으면 먼저 `intent-capture`로 만들어야 한다 — intent 없이 쓴 spec은 무엇을 왜 만드는지가 검증되지 않은 상태에서 설계부터 하는 것이다.
2. intent의 상태 줄이 `approved`인지 확인한다. `draft`라면 사용자에게 진행해도 되는지 묻는다.
3. 코드베이스를 읽는다. spec은 진공 상태의 설계가 아니라 **기존 코드베이스에 통합하기 위한** 설계다. 관련 모듈, 기존 패턴, 이미 있는 유사 기능을 파악한 뒤에 쓴다.

## 정책을 제약으로 적용한다

`.agents/skills/` 에 조직의 정책이 스킬로 인코딩돼 있다면 **먼저 읽고 제약으로 삼아라.** 흔히 있는 것들:

- 보안 표준 (인증 방식, PII 취급, 감사 이벤트)
- API 설계 규약
- UX / 접근성 기준
- 브랜드 가이드
- 컴플라이언스 요건

정책 스킬이 없다면 `AGENTS.md`와 코드베이스의 기존 패턴에서 추론하되, **추론했다는 사실을 spec에 명시하라.** 근거 없이 단정하면 나중에 리뷰에서 뒤집힌다.

### 충돌은 숨기지 말고 드러낸다

이게 이 스킬에서 가장 중요한 동작이다. 정책끼리 부딪히거나, 정책과 intent의 제약이 부딪히면 **한쪽을 임의로 골라 매끄럽게 봉합하지 마라.** `## Concerns` 섹션에 다음을 적는다:

- 무엇과 무엇이 충돌하는가
- 각 선택지가 무엇을 포기하는가
- 누가 판단해야 하는가

이 항목들이 원래 분석가가 위로 에스컬레이션했을 지점이다. 여기서 조용히 결정해버리면 조직이 그 결정을 인지하지 못한 채 코드가 나간다.

## 템플릿

섹션 제목은 영어로 고정하고 본문은 한국어로 쓴다.

```markdown
# Spec: 간편 로그인 개선
출처: docs/intent/002-social-login.md · 상태: draft

## Summary
Google·Apple OAuth 로그인을 추가해 신규 가입 경로를 단순화한다.
기존 이메일 로그인은 그대로 유지하며, 소셜 계정과 기존 계정의
중복 가입은 이메일 기준으로 차단한다.

## Requirements
### 기능 요구사항
- R1. 로그인 화면에 Google·Apple 버튼을 노출한다.
- R2. 최초 소셜 로그인 시 계정을 생성하고 즉시 세션을 발급한다.
- R3. 소셜 계정의 이메일이 기존 계정과 일치하면 가입을 차단하고
      기존 방식으로 로그인하도록 안내한다.

### 비기능 요구사항
- N1. OAuth 콜백 처리는 p95 800ms 이내.
- N2. 로그인 실패 사유를 사용자에게 노출하되 계정 존재 여부는
      추론할 수 없어야 한다.

## Design
### 흐름
1. 클라이언트가 provider 인증 페이지로 리다이렉트
2. 콜백을 auth-api가 수신, provider 토큰 검증
3. user-database에서 이메일 조회 → 신규/충돌 분기
4. 기존 세션 발급 로직 재사용

### 변경 지점
- auth-api: OAuth provider 추상화 계층 신규
- user-database: users 테이블에 provider, provider_uid 컬럼 추가
- mobile-app: 로그인 화면 버튼 추가

### 적용한 정책
- 보안 표준: provider 토큰은 로그에 남기지 않는다 (PII 분류)
- API 규약: 신규 엔드포인트에 게이트웨이 JWT 적용
- 접근성: 소셜 버튼에 명시적 label 제공

## Acceptance criteria
- AC1. 신규 Google 계정으로 가입 시 세션이 발급되고 홈으로 이동한다.
- AC2. 기존 이메일과 같은 Google 계정으로 시도하면 R3 안내가 뜬다.
- AC3. 인증 실패 시 provider 토큰이 어떤 로그에도 남지 않는다.

## Concerns
- C1. intent의 "새 PII를 수집하지 않는다"와 provider_uid 저장이
      충돌할 수 있다. provider_uid를 PII로 분류할지 판단 필요.
      → 판단 주체: 보안 담당
- C2. Apple의 이메일 가리기(private relay) 사용 시 R3의 이메일
      대조가 동작하지 않는다. 이 경우 정책 필요.
      → 판단 주체: Product Owner

## Open questions carried from intent
- 기존 이메일 계정과 소셜 계정 연결: 이번 범위에서 제외하되
  provider 컬럼 설계는 나중에 연결 가능하도록 남긴다.
```

## 작성 원칙

- **요구사항에는 번호를 붙인다.** plan.md와 리뷰가 이 번호를 참조한다. 번호가 없으면 "spec을 만족하는가"를 검증할 수 없다.
- **Acceptance criteria는 검증 가능한 문장으로 쓴다.** "빠르게 동작한다"가 아니라 "p95 800ms 이내"처럼. 이게 나중에 plan.md의 Proof 섹션과 테스트의 근거가 된다.
- **intent의 Open questions를 반드시 처리한다.** 답을 냈으면 어디에 반영했는지, 못 냈으면 왜 이월하는지를 적는다. 조용히 사라지면 안 된다.
- **구현 순서나 파일 목록은 여기 쓰지 않는다.** 그건 plan.md의 몫이다. spec은 "무엇을 만족해야 하는가"까지, plan은 "어떤 파일을 어떤 순서로"부터다.

## 프론트엔드 작업이라면

UI가 있는 작업은 문장만으로 설계를 확정하기 어렵다. spec을 쓰기 전이나 쓰면서 목업을 만들고, 그 목업을 spec에 첨부하거나 경로로 참조하라. 나중에 구현 단계에서 스크린샷과 목업을 대조하는 검증 루프의 기준이 된다.

## 저장 위치

```
docs/specs/
├── 001-claims-status.md
└── 002-social-login.md
```

**intent와 같은 번호·슬러그를 쓴다.** 이게 두 문서를 잇는 유일한 연결고리다. 문서 상단의 `출처:` 줄에도 intent 경로를 명시한다.

커밋 메시지는 `spec: 간편 로그인 개선` 형태로 통일한다.

## 규모별 차이

### 개인 / 소규모

- 스펙을 쓴 뒤 직접 검토하고 바로 커밋한다.
- Concerns는 그래도 적어라. 판단 주체가 본인이더라도, 무엇을 포기하기로 했는지 남겨두면 나중에 왜 그렇게 했는지 되짚을 수 있다.
- 정책 스킬이 없는 게 정상이다. 대신 반복해서 지키고 싶은 규칙이 생기면 그때 `.agents/skills/`로 승격시켜라.
- 작은 변경이면 spec을 건너뛰고 intent에서 바로 plan으로 가도 된다. 다만 그 결정을 매번 의식적으로 하라 — 기본값으로 굳으면 설계 없이 코딩하던 예전으로 돌아간다.

### 팀

- **스펙은 Product Owner가 쓰지 않고 리뷰한다.** 에이전트가 쓰고 PO는 "이 스펙이 원래 문제를 푸는가"를 본다.
- Concerns는 **엔지니어링에 넘기기 전에** 각 판단 주체와 해소한다. 미해결 Concern을 안고 plan으로 넘어가면 구현 중에 되돌아온다.
- 승인은 PR 머지로 기록한다. 상태 줄은 `draft`로 시작해 리뷰 승인 후 **머지 전에** `approved`로 바꾼다.
- 리스크가 높다고 분류된 변경은 PO 혼자 결정하지 말고 테크리드나 아키텍트를 끌어들여라. 무엇을 "높은 리스크"로 볼지는 조직이 미리 정해두는 게 좋다.
- 운영이 안정되면 이 단계를 자동화할 수 있다. intent PR이 머지되는 순간 비대화형 잡이 돌아 spec.md PR을 생성하게 만들면, PO의 첫 개입 지점이 리뷰가 된다. 다만 **처음부터 자동화하지 마라.** 손으로 몇 번 돌려서 프롬프트와 정책 스킬이 안정된 뒤에 붙인다.

## 흔한 실패

- **intent를 그대로 부풀리기.** 같은 내용을 섹션만 늘려 다시 쓴 건 spec이 아니다. spec에는 intent에 없던 것 — 요구사항 번호, 설계 결정, 수용 기준, 정책 적용 결과 — 이 들어가야 한다.
- **Concerns를 비워두기.** 정책이 여러 개 적용되는데 충돌이 하나도 없는 경우는 드물다. 비어 있다면 정책을 실제로 읽지 않았을 가능성이 높다.
- **코드베이스를 안 읽고 쓰기.** 기존에 이미 있는 추상화를 모르고 새로 설계하면 plan 단계에서 통째로 뒤집힌다.
- **구현 계획까지 밀고 나가기.** 파일 목록과 작업 순서가 나오기 시작하면 멈춰라. 그건 다음 스킬이다.

## 다음 단계

spec이 승인되면 `implementation-plan` 스킬로 넘긴다. 사용자에게 이렇게 안내하라:

> spec이 확정됐습니다. 다음은 파일을 수정할 수 없는 상태에서 구현 계획(plan.md)을 만들고 코드를 쓰기 전에 그 계획부터 검토하는 단계입니다. 진행할까요?
