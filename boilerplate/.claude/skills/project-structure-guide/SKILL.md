# 프로젝트 구조 안내

이 프로젝트의 구조에 대한 질문에 답한다. **아무것도 수정하지 않는다.**

사용자는 이 구조를 미리 공부하고 온 사람이 아니다. 쓰면서 익히는 중이며, 그래서 질문이
단편적으로 들어온다. 한 번에 전체를 가르치려 하지 말고 **물어본 것에 답한 뒤 바로 다음에 알
법한 것 하나만** 덧붙여라.

## 답하기 전에 읽을 것

질문의 성격에 따라 근거가 있는 파일이 다르다.

| 질문 | 읽을 곳 |
|---|---|
| "무엇을 어디에 쓰나" / "규칙이 뭔가" | `AGENTS.md` |
| **"왜 이렇게 되어 있나" / "안 지키면 어떻게 되나" / "바꿔도 되나"** | `docs/why-this-structure.md` |
| "이 도구에서는 어떻게 하나" | `CLAUDE.md`, `.codex/` |
| "이 프로젝트가 뭘 만드는 건가" | `AGENTS.md`의 `## 프로젝트` 절, `README.md` |
| "문서를 어떻게 쓰나" | `docs/templates/` 의 빈 양식, 그리고 해당 단계의 스킬 |

`docs/why-this-structure.md`가 이 스킬의 핵심 근거다. 규칙만 반복하고 이유를 대지 못하는 답은
사용자를 납득시키지 못하며, 납득하지 못한 규칙은 첫 불편함을 겪는 순간 폐기된다.

## 답할 때의 규율

**1. 도구 제약과 팀의 선택을 구분해서 말하라.**

`docs/why-this-structure.md`의 각 항목에는 "근거 유형"이 붙어 있다.

- **도구 제약** — 공식 문서로 확인된 사실이고 출처 URL이 있다. "바꿀 수 없습니다"라고 단정해도 된다.
- **팀의 선택** — 이 구조를 만든 사람들이 정한 것이다. **"팀이 정한 것이라 바꿀 수 있습니다"라고
  반드시 밝혀라.**

둘을 같은 확신으로 말하면 사용자는 바꿔도 되는 것을 못 바꾸고, 못 바꾸는 것을 바꾼다.

**2. 근거가 문서에 없으면 없다고 말하라.** 그럴듯한 이유를 지어내지 마라. "그건 문서에 근거가
없습니다. 팀에서 정한 뒤 `docs/decisions/`에 남기시면 됩니다"가 정확한 답이다.

**3. "안 지켜도 되나요"에는 결과로 답하라.** 금지를 반복하지 말고 어기면 무슨 일이 생기는지를
말하라. `docs/why-this-structure.md`의 "어기면" 항목이 그 답이다.

**4. 사용자의 역할에 맞춰라.** 기획·비개발 직군이면 `docs/intent/`와 문서 흐름부터 답하고
스킬 동기화 같은 이야기는 꺼내지 마라. 개발자면 파이프라인과 승인 게이트가 먼저다.

## 처음 합류한 사람이 "구조 설명해줘"라고 하면

전부 늘어놓지 말고 이 순서로, 각 항목을 두세 문장으로 말한 뒤 **더 볼지 물어라.**

1. **이 프로젝트가 무엇을 만드는가** — `AGENTS.md`의 `## 프로젝트` 절
2. **작업이 흐르는 순서** — 왜(`docs/intent/`) → 무엇(`docs/specs/`) → 어떻게(`docs/plans/`) → 구현.
   세 문서는 같은 번호를 공유하고, 그 번호가 PR과 `CHANGELOG.md`까지 이어진다
3. **규칙이 어디 있는가** — `AGENTS.md` 하나가 기준이다. 다른 지침 파일은 이것을 참조만 한다
4. **지금 당장 할 일이 있다면 무엇으로 시작하는가** — 무엇을 왜 만들지가 아직 문서로 고정되지
   않았다면 intent부터다

그 자리에서 다 이해시키려 하지 마라. **"작업하다 막히면 그때 물어보세요"가 이 구조의 사용법이다.**

## 자주 나오는 질문

**"스킬이 왜 두 폴더에 똑같이 있나요?"** — 도구마다 읽는 경로가 달라서다. 수정은 항상
`.agents/skills/`에서 하고 동기화 스크립트를 돌린다. 미러를 직접 고치면 다음 동기화 때 사라진다.
근거는 `docs/why-this-structure.md`의 "스킬이 두 폴더에 중복으로 들어 있는 이유".

**"문서를 세 개나 써야 하나요?"** — 규모가 작으면 합치거나 건너뛸 수 있다. 다만 건너뛰는 판단을
매번 의식적으로 해야 한다. 근거는 "문서를 intent → spec → plan 셋으로 나누는 이유". 여기서 "귀찮다"는 반응이 나오면 규칙을 강요하지 말고
**되돌리는 비용** 이야기를 하라 — 문단을 고치는 것과 코드를 버리는 것의 차이다.

**"이 폴더 안 쓰면 지워도 되나요?"** — `docs/` 아래는 대체로 조정 가능하고, 루트의 도구 관련
항목은 옮기면 도구가 조용히 동작을 멈춘다. "루트에 있는 것과 `docs/` 아래로 내린 것"의 표로 답하라.

**"설정이 안 먹어요"** — Codex는 프로젝트를 신뢰(trust)로 표시하기 전까지 `.codex/` 설정을 전부
무시한다. 이 질문의 가장 흔한 원인이다.

## 하지 않는 것

- **파일 수정.** 이 스킬은 읽고 답하기만 한다. 사용자가 수정을 원하면 무엇을 고쳐야 하는지
  알려주되, 실제 변경은 별도 작업으로 진행한다
- 초기 설정 채우기 — 그건 `project-bootstrap`이다
- 근거 없는 추측을 사실처럼 말하기
- 묻지 않은 것까지 전부 설명하기
