# Intent 포착 (intent.md)

`intent.md`는 완성된 PRD가 아니라 **proto-spec**이다. 무엇을 만들지가 아니라 **왜 만드는지**를 발의자(originator)의 언어로 고정하는 문서다.

이 단계가 중요한 이유는 구현 비용이 싸졌기 때문이다. 에이전트가 몇 분 만에 코드를 써주는 환경에서는 **잘못 정의된 문제를 아주 빠른 속도로 구현해버리는 것**도 가능해진다. 그래서 문제 정의가 예전보다 더 중요해졌다.

## 핵심 규율: 여기서는 코드 이야기를 하지 않는다

intent 단계에서 다뤄야 할 것과 다루면 안 되는 것이 명확히 갈린다.

| 다룬다 | 다루지 않는다 |
|---|---|
| 지금 무엇이 안 되는가 | 어떤 라이브러리를 쓸까 |
| 누구의 문제인가 | DB 스키마를 어떻게 바꿀까 |
| 어떻게 달라져야 하는가 | 컴포넌트 구조를 어떻게 짤까 |
| 무엇은 하면 안 되는가 | API 엔드포인트를 어떻게 설계할까 |

사용자가 먼저 구현 이야기를 꺼내면 받아 적지 말고 되물어라. "그 방법은 spec 단계에서 정하면 됩니다. 지금은 그게 왜 필요한지부터 확정하시죠." 구현 아이디어가 아깝다면 `## Open questions`에 힌트로만 남겨라.

## 절차

### 1. 인터뷰한다 — 이게 이 스킬의 본체다

곧바로 파일을 쓰지 마라. **분석가가 물었을 사항을 다 물어볼 때까지** 대화한다. 한 번에 하나나 둘씩, 대화하듯이 묻는다.

물어야 할 것:

- **문제**: 지금 무엇이 안 되나? 얼마나 자주, 얼마나 심하게 발생하나? 근거가 되는 수치나 사례가 있나?
- **영향 대상**: 누가 겪는 문제인가? 몇 명인가? 내부 사용자인가 고객인가?
- **영향받는 시스템**: 어떤 서비스·레포·팀이 얽혀 있나?
- **원하는 결과**: 이게 해결되면 무엇이 달라지나? 성공했다는 걸 어떻게 알 수 있나?
- **제약**: 건드리면 안 되는 것은? 유지해야 하는 동작은? 규제·보안·호환성 제약은?
- **범위 밖**: 이번에 하지 않을 것은 무엇인가?

사용자가 "그건 잘 모르겠는데요"라고 하면 억지로 채우지 말고 `## Open questions`로 옮겨라. 미해결 질문을 정직하게 남기는 게 추측으로 채우는 것보다 낫다. 이 항목들은 spec 단계에서 답변되거나 그대로 이월되며, 그 여부 자체가 리뷰 체크포인트가 된다.

**인터뷰를 끝낼 시점**: 이 대화를 못 본 사람이 문서만 읽고 "무슨 문제를, 누구를 위해, 어떤 제약 아래 푸는지"를 정확히 이해할 수 있을 때.

### 2. 초안을 쓴다

아래 템플릿으로 작성한다. 섹션 제목은 영어로 고정하고 본문은 한국어로 쓴다 — 제목이 고정돼야 다음 단계의 에이전트가 안정적으로 파싱한다.

```markdown
# Intent: 간편 로그인 개선
작성자: 김민수 (그로스팀) · 상태: draft

## Problem
신규 사용자의 회원가입 과정에서 인증 단계 이탈률이 높다.
지난달 가입 시도 4,200건 중 인증 화면에서 1,100건이 이탈했다.

## Proposed outcome
Google과 Apple 로그인을 추가해 가입 과정을 단순화한다.
인증 단계 이탈률을 절반 이하로 낮추는 것이 목표다.

## Affected users and systems
신규 가입 사용자 / auth-api, mobile-app, user-database

## Constraints
기존 계정과 소셜 계정의 중복 가입을 허용하지 않는다.
현재 세션 구조는 그대로 유지한다.
새로운 PII를 수집하지 않는다.

## Out of scope
기존 사용자의 계정 이전. 관리자 로그인.

## Open questions
기존 이메일 계정을 나중에 소셜 계정과 연결할 수 있게 할 것인가?
```

**분량 기준**: 한 화면에 들어와야 한다. 길어진다면 문제를 여러 개 뭉쳐놓은 것이니 intent를 쪼개라.

### 3. 발의자에게 확인받는다

초안을 보여주고 **잘못 이해한 부분이 있는지** 명시적으로 묻는다. 이 확인 단계를 건너뛰면 안 된다 — 발의자의 의도를 에이전트가 요약하는 과정에서 뉘앙스가 바뀌는 일이 흔하고, 그 왜곡이 spec과 plan을 거치며 증폭된다.

### 4. 저장하고 커밋한다

`docs/intent/` 폴더에 저장한다. 파일명은 `NNN-슬러그.md` 형식으로, 번호는 기존 파일 중 가장 큰 번호 다음을 쓴다.

```
docs/intent/
├── 001-claims-status.md
├── 002-social-login.md
└── 003-slow-dashboard.md
```

작성자와 타임스탬프는 git이 기록하므로 문서 안에서 따로 관리하지 않는다. 상단의 `작성자 · 상태` 줄만 예외다 — 발의자가 git을 쓰지 않는 사람일 수 있어 커밋 작성자와 다르고, 상태 줄은 다음 단계의 스킬이 진행해도 되는지를 판단하는 근거다.

커밋 메시지는 `intent: 간편 로그인 개선` 형태로 통일한다.

## 규모별 차이

절차 1~3은 규모와 무관하게 같다. 달라지는 건 4번 이후다.

### 개인 / 소규모

- 발의자 = 승인자다. 확인 후 바로 main에 커밋한다.
- 상태 줄은 `draft`로 두었다가 확정되면 `approved`로 바꾼다. 진행 상태(작업 중·완료)를 추적하고 싶다면 그건 상태 줄이 아니라 다른 수단을 쓴다.
- intent를 여러 개 쌓아두고 우선순위를 매기고 싶다면 `docs/intent/README.md`에 목록을 두거나, 파일명 앞에 우선순위를 붙여도 된다.
- Open questions가 남아 있어도 진행해도 된다. 혼자라면 spec을 쓰면서 답을 정하면 된다.

### 팀

- 발의자와 승인자가 다르다. 발의자는 개발자가 아니어도 된다 — 버그를 신고하는 고객, 아이디어가 있는 PM, 프로세스 개선을 떠올린 디자이너 누구나 발의자가 될 수 있다. 이 경우 사용자가 git을 모른다고 전제하고, 파일 내용을 그대로 보여준 뒤 커밋은 대신 처리하라.
- intent는 **PR로 올린다**. Product Owner가 리뷰하고 머지하는 행위가 곧 "Stage 2로 진행" 승인이다. 닫히면 반려다.
- 상태 줄은 `draft`로 두고, 리뷰 승인 후 **머지 전에** `approved`로 바꾼다. PR이 열려 있는지 닫혔는지는 PR 자체가 기록하므로 문서에 옮겨 적지 않는다.
- Open questions에 정책·보안·법무 판단이 필요한 항목이 있으면, 누구에게 물어야 하는지까지 문서에 적어라. spec 단계에서 이게 병목이 된다.
- 조직에 Jira나 ServiceNow가 이미 있다면 없애지 말고 **어느 쪽이 원본인지 하나만 정하라.** 최소 기준은 intent.md에 티켓 ID를 적고 티켓에 커밋 SHA를 남겨 양방향으로 연결하는 것이다.

## 흔한 실패

- **티켓을 그대로 옮겨 적기.** 한 줄짜리 요청을 그대로 Problem에 붙여넣는 건 intent가 아니다. 인터뷰 없이 나온 intent는 이 스킬을 쓰지 않은 것과 같다.
- **해결책을 문제로 위장하기.** "소셜 로그인이 없다"는 문제가 아니라 이미 결정된 해결책이다. 진짜 문제는 "가입 과정에서 이탈이 많다"다. Problem에 특정 해법이 박혀 있으면 되물어라.
- **Constraints를 비워두기.** 제약이 없는 intent는 없다. 최소한 "기존 동작 중 깨지면 안 되는 것"은 반드시 하나 이상 나온다.
- **Open questions를 억지로 비우기.** 빈 칸이 깔끔해 보인다고 추측으로 채우면 그 추측이 spec에서 사실로 굳는다.

## 다음 단계

intent가 승인되면 `spec-authoring` 스킬로 넘긴다. 사용자에게 이렇게 안내하라:

> intent가 확정됐습니다. 다음은 이걸 spec.md로 옮기면서 보안·UX·컴플라이언스 정책을 적용하는 단계입니다. 바로 진행할까요?

## 자동화된 유지보수 흐름에서 이 스킬을 쓸 때

모니터링 스크립트나 장애 진단 결과가 intent를 만드는 경우에도 형식은 동일하다. 다만 인터뷰할 사람이 없으므로:

- Problem에 이상 징후와 **근거 데이터**(지표명, 임계값, 관측된 값, 시각)를 적는다.
- Affected systems에 배포 이력이나 관련 서비스를 적는다.
- 확신할 수 없는 원인 추정은 단정하지 말고 Open questions로 내린다.
- 상태는 `draft`로 두고 사람이 검토하도록 남긴다. 자동으로 만들어진 intent는 사람이 승인하기 전까지 `approved`가 되지 않는다.
